# PRODUCTION_DEPLOYMENT.md — deploying X on Render

This guide reproduces a fresh production deployment from this repository. Everything runs on Render: two web services, one background worker, PostgreSQL and Key Value (Redis).

```
x-web  (Node, Next.js)  ──/api proxy──▶  x-api (Python, FastAPI) ──▶ x-db (PostgreSQL)
   └── browser WebSocket (ticketed) ───────▶  x-api                ──▶ x-redis (rate limits)
                                              x-worker (python -m app.worker) ──▶ x-db
```

## 1. Prerequisites

- The repository is pushed to GitHub or GitLab and connected to Render.
- A Fernet key for credential encryption. Generate it once and store it safely. Changing it later makes stored credentials unreadable.
  ```bash
  python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
  ```
- An email address and password for the first super administrator. The password needs 12 or more characters, mixed case, and a digit.
- Optional: an Anthropic API key, or any other provider key, which you can instead enter later in Admin → AI Management.

## 2. Create the services from the Blueprint

1. In Render, go to **New → Blueprint**, select the repository, and confirm `render.yaml`.
2. Render creates `x-db`, `x-redis`, `x-api`, `x-worker` and `x-web`. Before the first deploy it prompts for the `sync: false` values:

| Service | Variable | Value |
|---|---|---|
| x-api, x-worker | `X_ENCRYPTION_KEY` | the Fernet key from step 1. Use **the same value on both.** |
| x-api, x-worker | `X_FRONTEND_ORIGIN` | `https://x-web.onrender.com` (your x-web URL) |
| x-api, x-worker | `X_BOOTSTRAP_ADMIN_EMAIL` / `X_BOOTSTRAP_ADMIN_PASSWORD` | first super administrator |
| x-api, x-worker | `ANTHROPIC_API_KEY` | optional |
| x-web | `X_BACKEND_URL` | `https://x-api.onrender.com` (your x-api URL) |
| x-web | `NEXT_PUBLIC_WS_BASE` | `wss://x-api.onrender.com` |

`X_SECRET_KEY` is generated by Render for each service. The worker never signs sessions, so a different value there is harmless. `X_ENCRYPTION_KEY` **must** be identical on x-api and x-worker, because the worker decrypts provider credentials to run jobs.

3. Deploy. On start, x-api:
   - refuses to start if the production configuration is unsafe (weak secret, missing encryption key, SQLite, non-secure cookies);
   - runs `alembic upgrade head`, creating 54 tables and the guardrail triggers;
   - seeds roles and permissions, the X Layers v0.3B framework (10 layers, 93 rules, published only after validation), the AI and quantum provider registries (inactive until configured) and the scenario library;
   - creates the bootstrap super administrator.

   x-worker waits until the schema exists, then polls `background_jobs`.

## 3. Verify the deployment

1. `https://x-api.onrender.com/health` returns `{"ok": true}`.
2. `https://x-api.onrender.com/api/system/status` shows `intellect.version = v0.3B`, `rules = 93`, `protected = 10`, and the local quantum provider as `healthy`.
3. Open `https://x-web.onrender.com`, sign in as the bootstrap administrator, and watch the initialisation sequence.
4. Run **Energy Load Balancing** in *Classical* mode. The live console should stream events and the run should complete with a proven optimum.
5. Run it in *Comparative Benchmark* mode. The quantum step should be labelled **Local quantum simulator**.
6. Remove `X_BOOTSTRAP_ADMIN_PASSWORD` from both services after the first sign-in. The account remains.

## 4. Activate real integrations

| Integration | Where | Notes |
|---|---|---|
| Anthropic / OpenAI / Gemini / Azure OpenAI / Ollama / LM Studio | Admin → AI Management → provider → **Set credential**, toggle **Active**, **Check health** | Credentials are Fernet-encrypted and shown masked. Health is "healthy" only after a real call succeeds. |
| IBM Quantum, Amazon Braket, Azure Quantum, D-Wave, Google | Install the SDK (`requirements-quantum.txt`, then change the Render build command to `pip install -r requirements-quantum.txt`), then Admin → Quantum Management → credential, activate, **Sync registry** | Providers report `sdk missing` or `no credentials` until both are in place. Hardware runs also require the orchestration policy `allow_hardware` and a scenario policy that permits hardware, plus a cost cap above 0. |
| Deterministic test provider | Admin → AI Management → "X Test Provider" → Active | For offline walkthroughs only. Every result it produces is labelled **Test provider** and the execution's `result_source` is `test`. |

## 5. Operations

- **Backups.** Render PostgreSQL takes daily backups on paid plans. To restore, use Render dashboard → x-db → Recovery. For a manual dump, run `pg_dump "$DATABASE_URL" > x.sql`.
- **Recovery after a worker crash.** On start, a worker fails any job whose heartbeat is more than 20 minutes old, and marks its execution `failed` with "worker lost during execution". Users can resubmit.
- **Scaling.** Add x-worker instances freely: jobs are claimed with an atomic conditional update. x-api can scale horizontally because rate limits live in Redis and sessions in PostgreSQL.
- **Observability.** Use Render logs for x-api and x-worker. Every 500 response carries an `X-Request-ID` that matches the log line. Admin → Audit Log covers configuration, framework, rule, scenario, execution, authentication and security events.
- **Rotating `X_SECRET_KEY`** signs everyone out. **Rotating `X_ENCRYPTION_KEY`** requires re-entering every provider credential.
- **Migrations.** Add an Alembic revision under `backend/migrations/versions/`. The API applies it on its next deploy.

## 6. Local development

```bash
# backend
cd backend
python -m venv .venv && .venv/Scripts/pip install -r requirements-dev.txt   # (bin/pip on macOS/Linux)
cp .env.example .env          # set X_SECRET_KEY and the bootstrap admin
.venv/Scripts/python -m uvicorn app.main:app --port 8000
.venv/Scripts/python -m pytest        # 122 tests, no network, no paid APIs

# frontend
cd frontend
npm install
cp .env.example .env.local
npm run dev                   # http://localhost:3000
```
